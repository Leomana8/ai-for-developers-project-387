# UI-тестирование пользовательских сценариев

Прогоняешь приложение как реальный пользователь в настоящем браузере и ищешь
дефекты, которые не видны ни в коде, ни в unit-тестах: краши на кривых URL,
залипшие лоадеры, перепутанные тексты ошибок, неэкранированный ввод, вёрстку,
съезжающую на мобильном.

Ценность этого подхода — в расхождении между тем, что страница обещает, и тем,
что сервер и API реально делают. Именно на таких стыках находятся баги, поэтому
сценарии проверяют не «красивость», а конкретные ожидаемые значения: числа
свободных слотов, коды ошибок, точные тексты.

## Окружение

- Node.js 22.12+, npm workspaces.
- MCP-сервер `playwright` (инструменты `playwright_browser_*`).
- `gh` CLI авторизован — нужен для заведения багов (см. `docs/agents/issue-tracker.md`).

## Шаг 0. Поднять стек и узнать порт

Запусти `npm run dev` из корня репозитория **в фоне** и дождись строк
`VITE ready` и `Server is listening`.

Порт Vite **не хардкодь**. Если 5173–5176 уже заняты (часто у пользователя или
в соседнем агенте висят свои дев-серверы), Vite молча занимает следующий свободный.
Возьми порт из строки `Local: http://localhost:PORT` в выводе. Все дальнейшие
переходы — на этот порт.

Сервер всегда на `:3001`. Фронт ходит на него через прокси Vite по путям `/api/*`,
так что в браузере ты работаешь только с относительными `/api/*` — прямых
`http://localhost:3001` в адресной строке быть не должно.

**Не трогай чужие процессы.** Останавливать сервер (Шаг 6, группа H) можно
только через `netstat -ano | findstr ":3001"` → `taskkill /PID <свой PID> /T /F`.
Не делай `taskkill /IM node.exe` — у пользователя могут быть другие дев-серверы.

## Шаг 1. Пройти матрицу сценариев

Прочитай `references/scenarios.md` — это чек-лист групп A–I (~66 проверок).
Каждый пункт записан как «действие → ожидание». **Проверяй ожидание, а не
внешний вид**: если счётчик показывает `·32`, а занято 3 слота из 36 — это баг.

Иди по группам строго A → I. Причина в порядке:

- **A–G** накапливают данные: брони в D/C занимают слоты, которые нужны для
  проверки занятости в A, а типы, созданные в G, используются для проверки
  сетки слотов в A.
- **H** (сбои и рестарт) обнуляет in-memory хранилище сервера — после рестарта
  созданные тобой типы и брони исчезнут. Поэтому H идёт последним.
- Внутри групп порядок менее критичен, но сценарии «конфликт → проверка занятости
  в календаре» держи рядом.

**Идентификаторы доставай в рантайме.** Типы событий имеют UUID, которые
меняются при каждом рестарте сервера. Не хардкодь их — читай из API:

```
GET /api/event-types → [{id, name, duration}, …]
GET /api/meetings    → [{id, eventTypeId, start, guestEmail}, …]
```

**Готовь состояние через API там, где сценарий требует «занятого» дня.** Чтобы
проверить полностью занятый день, не бронируй вручную 18 слотов — создай их
циклом `POST /api/meetings` напрямую на `:3001`. Это и быстрее, и не зависит от
состояния браузера.

## Шаг 2. Работа с инструментами Playwright

Здесь почти всё неочевидно. Прежде чем писать проверки, прочитай этот раздел —
ошибки в нём стоят реального времени.

### Снапшот возвращает строку, а не объект

`playwright_browser_snapshot` отдаёт **строку** с markdown-YAML деревом.
Обращение `snapshot.snapshot` даст `undefined`. Обращайся к результату напрямую:

```js
const s = String(await tools.playwright.browser_snapshot({}))
// s.split('\n'), s.match(...) — работает
```

### `browser_click` принимает `{ element, target }`, а не `{ ref }`

Имя ключа — `target`. Значение — ref из снапшота (`e42`) **или** уникальный
селектор. Поле `element` — человекочитаемое описание, оно нужно для разрешений.

### Ref из снапшота протухают между вызовами

Между `browser_snapshot` и `browser_click` страница успевает перерисоваться, и
ref перестаёт существовать: `Error: Ref e452 not found in the current page
snapshot`. Это источник нестабильных «мигающих» прогонов.

**Для взаимодействий используй `browser_run_code_unsafe` с локаторами
Playwright** — они ищут элемент в момент выполнения и не протухают:

```js
await tools.playwright.browser_run_code_unsafe({
  code: `async (page) => {
    await page.getByRole('button', { name: 'Записаться' }).click()
    return 'ok'
  }`,
})
```

Локаторы — надёжнее и для цепочек: `await page.getByRole('heading', {name: 'Вы записаны!'}).waitFor()`.
Возвращай из функции **строку с результатами всех проверок сразу** (`out.push(...)`),
чтобы не терять вывод при таймауте посередине.

Снапшот оставь для **чтения состояния** (что отрисовано, какие тексты) — там он
надёжен, потому что ты его только читаешь.

### `wait_for` ищет видимый текст, а не `aria-label`

`browser_wait_for({ text: 'Слоты на 12 октября' })` зависнет: это `aria-label`
региона, а не текст. Жди по видимому заголовку дня (`'12 октября'`) или
используй локаторы с `waitFor` внутри `run_code_unsafe`.

### `fetch` внутри страницы отдаёт кэш — нужен `no-store`

`page.evaluate(() => fetch('/api/meetings'))` может вернуть **устаревший** ответ:
Express не шлёт `Cache-Control`, и браузер применяет эвристическое кэширование.
Ты снимешь «проверку» на данных, которых ещё нет, и решишь, что запись не создалась.

```js
page.evaluate(() => fetch('/api/meetings', { cache: 'no-store' }).then((r) => r.json()))
```

Для сверок с сервером удобнее вообще обращаться напрямую из агента через `fetch`
к `http://localhost:3001/api/...` — это всегда актуальные данные и не зависит от
состояния страницы.

### Ошибки в консоли — источник находок

В конце прогона собери консоль целиком и **отфильтруй шум**:

```js
String(await tools.playwright.browser_console_messages({ level: 'error', all: true }))
```

`Failed to load resource: 409/422/502` — это ожидаемые ответы от намеренных
негативных сценариев, не дефект. Реальные находки — RangeError, «Error handled
by React Router default ErrorBoundary», React warnings.

### Мобильный вьюпорт — проверяй переполнение числом, не на глаз

```js
await page.setViewportSize({ width: 375, height: 667 })
const overflow = await page.evaluate(
  () => document.documentElement.scrollWidth - document.documentElement.clientWidth,
)
```

`overflow <= 0` — страница помещается. Прогонь это по всем экранам: провалится
именно на одном, и искать вручную долго.

## Шаг 3. Отчёт

Отчёт — основной артефакт прогона. Пиши его в чат по этому шаблону:

```markdown
# Отчёт: UI-тестирование

**Стек:** Vite (:PORT) + Express (:3001), Chromium, 375×667 и 1280×800.
**Проверок:** N, пройдено M, дефектов K.

## Дефекты

| #   | Приоритет | Дефект | Где         |
| --- | --------- | ------ | ----------- |
| 1   | 🔴 P1     | …      | `file:line` |

## Результаты по группам

**A. …** — краткий итог группы: что подтвердилось, что упало.

## Примечания

- Что исключено и почему (например: не проверяется без сдвига часов).
- Состояние окружения после прогона.
```

Приоритеты:

- **P1** — краш или полная неработоспособность экрана.
- **P2** — экран залипает в лоадере или показывает неверное сообщение.
- **P3** — неверная локализация, вёрстка, доступность.
- **P4** — спорное поведение API, вопрос к спецификации.

Дефекты описывай как тикеты: **что случилось → как воспроизвести → ожидание vs
факт → причина (файл и функция) → объём фикса → критерии готовности**. Баг без
воспроизведения и без указания причины бесполезен тому, кто будет чинить.

## Шаг 4. Завести баги в Issues

Спроси у пользователя, стоит ли заводить тикеты, и **предложи готовый текст**
для каждого дефекта. Регламент — `docs/agents/issue-tracker.md`,
лейблы — `docs/agents/triage-labels.md`.

Заголовок — conventional commit, как принято в репозитории:

```
fix(web): краш подтверждения при невалидном start= в URL (RangeError: Invalid time value)
```

Команды:

```
gh issue create --title '<заголовок>' --body-file '<файл>' --label bug --label ready-for-agent
```

Ловушка, которая уже стоила времени: **символ `?` в `--title` ломает shell-сканер**
(`Portable shell scanner cannot analyze command: invalid-structure`), и это выглядит
как ошибка самого `gh`. Обходи двумя способами — либо не пиши `?` в заголовке,
либо создай с безопасным заголовком и поправь:

```
gh issue edit <number> --title '...'
```

Пиши тело в файл (`--body-file`), а не в `--body`: многострочные строки с
кириллицей, кавычками и эмодзи в аргументах ломаются по кодировке.

Ставь `ready-for-agent`, только если дефект действительно полностью
специфицирован — с воспроизведением, причиной и критериями готовности.
Спорные вопросы к спецификации (например, принимает ли сервер `user@localhost`)
создавай как `needs-triage`: решение по ним принимает человек, а не агент.
