# Клиентский SDK фронта: openapi-typescript + openapi-fetch

ADR-0003 зафиксировал TypeSpec как единственный источник истины об API и генерацию
OpenAPI как артефакта сборки. Следующий шаг, предсказанный там же («позже —
кодогенерация клиентов»), — типизированный клиент для фронтенда, чтобы `fetch`-вызовы
не расходились с контрактом.

## Considered Options

- **Рукописный слой `fetch` + ручные типы** — отвергнуто: дублирует модели из
  спеки, типы молча расходятся с контрактом при изменении API.
- **`@typespec/http-client-ts` (генерация клиента из TypeSpec)** — отвергнуто:
  тяжелее по настройке, собирает полноценный SDK-пакет, а не типы; клиент по
  умолчанию завязывается на `@server` URL и требует отдельной настройки
  относительного `/api`. Выгода «единого источника» не компенсирует сложности.
- **`@hey-api/openapi-ts`** — отвергнуто: генерирует именованный SDK с собственным
  стилем (`client.gen.ts`), избыточно для текущего объёма API.
- **`openapi-typescript` + `openapi-fetch`** — выбрано: из закоммиченного
  `spec/output/openapi.yaml` генерируется один файл типов `schema.d.ts`; рантайм —
  тонкий типизированный `fetch`-клиент (совместимо с «чистым fetch» из постановки
  слоя данных). Минимум зависимостей, база URL настраивается.

## Consequences

- Единственный источник истины об API остаётся `spec/*.tsp`; типы клиента —
  артефакт сборки из `spec/output/openapi.yaml`. `npm run spec:client` генерирует
  `apps/web/src/api/schema.d.ts`, `npm run spec:client:check` — drift-check в CI
  (по аналогии с `spec:check`).
- Клиент создаётся с пустой базой URL (`createClient<paths>()`): запросы уходят
  относительными `/api/*` и проксируются Vite; абсолютных URL в коде нет (AGR-0001,
  правило AGENTS.md).
- Генерируемый `schema.d.ts` не форматируется Prettier и не правится вручную
  (исключён в `.prettierignore`).
- Типы ответов (`Health.status`, `Availability`, `Meeting` и др.) проверяются на
  этапе компиляции — расхождение контракта и фронта ловится сборкой.
